# depgraph — визуализатор графа зависимостей пакетов NuGet

CLI-инструмент на Python, который строит граф зависимостей пакета формата
.NET (NuGet), печатает его в виде списка, ASCII-дерева и порядка загрузки, а
также рисует диаграмму PlantUML и сохраняет её в PNG.

Зависимости получаются напрямую из репозитория по HTTP (`.nuspec`), **без**
менеджеров пакетов (`dotnet`, `nuget`) и сторонних библиотек. Используется
только стандартная библиотека Python.

## Требования

- Python 3.8 или новее.
- Для PNG — одно из двух:
  - **`plantuml.jar`** + Java + Graphviz (`dot`): `--plantuml-jar путь/plantuml.jar`
    (работает офлайн);
  - либо доступ в интернет: без `--plantuml-jar` изображение запрашивается
    у сервера PlantUML (`https://www.plantuml.com/plantuml`).
- Для реального режима — доступ к `https://api.nuget.org/v3/index.json`.
  Тестовый режим работает без сети.

## Структура репозитория

```
src/
    main.py             исходный код программы
tests/
    test_main.py        модульные тесты (unittest)
examples/
    repo.txt            пример тестового репозитория
run.sh, run.bat         запуск программы и тестов
.gitignore
README.md
```

## Запуск

Через скрипт (Linux/macOS: `./run.sh`, Windows: `run.bat`):

```
./run.sh -p A -r examples/repo.txt -t -a
./run.sh test
```

Или напрямую:

```
python3 src/main.py -p A -r examples/repo.txt -t -a
python3 -m unittest discover -s tests -v
```

## Параметры командной строки

| Опция | Описание |
|---|---|
| `-p`, `--package` | имя анализируемого пакета (обязательно) |
| `-r`, `--repo` | URL репозитория (service index NuGet v3) или путь к файлу тестового репозитория (обязательно) |
| `-t`, `--test-mode` | тестовый режим: `--repo` — путь к файлу описания графа |
| `-v`, `--version` | версия пакета, например `13.0.3` (вне тестового режима обязательна) |
| `-o`, `--output` | имя PNG-файла с графом, по умолчанию `graph.png` |
| `-a`, `--ascii-tree` | вывести зависимости в виде ASCII-дерева |
| `-f`, `--filter` | подстрока: пакеты, в имени которых она есть (без учёта регистра), не анализируются |
| `-l`, `--load-order` | вывести порядок загрузки зависимостей (вместо графа и изображения) |
| `--plantuml-jar` | путь к `plantuml.jar`; без него PNG строится через сервер PlantUML |

Все параметры проверяются при запуске; найденные ошибки выводятся списком.

## Примеры

Реальный репозиторий:

```
python3 src/main.py -p Newtonsoft.Json -r https://api.nuget.org/v3/index.json -v 13.0.3
python3 src/main.py -p Serilog.Extensions.Logging -r https://api.nuget.org/v3/index.json -v 8.0.0 -a
```

Тестовый репозиторий:

```
python3 src/main.py -p A -t -r examples/repo.txt -a
python3 src/main.py -p A -t -r examples/repo.txt -f B
python3 src/main.py -p A -t -r examples/repo.txt -l
python3 src/main.py -p A -t -r examples/repo.txt -a -o graph.png --plantuml-jar plantuml.jar
```

Пример вывода (`examples/repo.txt`, `-a`):

```
Граф зависимостей пакета A: пакетов 4, рёбер 5
  A -> B, C
  B -> D
  D -> (нет зависимостей)
  C -> D, A
Циклические зависимости (1):
  A -> C -> A

ASCII-дерево зависимостей:
A
├── B
│   └── D
└── C
    ├── D
    └── A (цикл)
(*) — поддерево показано выше; (цикл) — возврат к пакету-предку
```

## Формат тестового репозитория

Текстовый файл, по одной строке на пакет: `ИМЯ: зависимости через пробел`.
Имена — заглавные латинские буквы. Пустые строки и `#` комментарии
игнорируются. Пакет без зависимостей записывается как `D:`.

```
# пример
A: B C
B: D
C: D A
D:
```

Ошибки файла (неверный формат, строчные буквы, повторное описание, пустой
файл) сообщаются с номером строки.

## Как это работает

1. **Получение данных.** Из service index NuGet v3 берётся ресурс
   `PackageBaseAddress`, затем скачивается `{base}/{id}/{version}/{id}.nuspec`
   и разбирается через `xml.etree`. Учитываются разные пространства имён
   `.nuspec`, группы по target framework и зависимости без групп.
2. **Версии.** Диапазон версии (`[1.0, )`, `(, 2.0]`) заменяется нижней
   границей.
3. **Граф.** Рекурсивный DFS. Пакеты с подстрокой фильтра пропускаются вместе
   с их поддеревьями. Ребро в пакет, который сейчас в стеке рекурсии,
   сохраняется и фиксируется как цикл, но рекурсия в него не идёт; уже
   обработанный пакет не раскрывается повторно.
4. **Порядок загрузки.** Пост-порядок DFS: пакет идёт после всех своих
   зависимостей, корень последний. Циклы разрываются по обратному ребру, и
   программа сообщает, по каким.
5. **Визуализация.** Текст PlantUML (`.puml` сохраняется рядом с PNG; рёбра
   цикла — красный пунктир), затем PNG через `plantuml.jar` или сервер
   PlantUML. ASCII-дерево строится рекурсивным обходом.

## Коды возврата

| Код | Значение |
|---|---|
| 0 | успех |
| 2 | ошибка параметров командной строки |
| 3 | ошибка репозитория (сеть, 404, некорректные данные, ошибка файла тестового репозитория) |
| 4 | ошибка построения PNG (`.puml` при этом сохраняется) |

## Упрощения и ограничения

Эти пункты определяют, чем результат отличается от реального менеджера
пакетов:

- **Версии.** Узел графа определяется именем пакета; при нескольких версиях
  одного пакета берётся первая встреченная. NuGet выбирает версию иначе
  (nearest wins, при конфликтах — наибольшая из нижних границ).
- **Target framework.** Зависимости объединяются по всем группам `.nuspec`, а
  `dotnet` берёт только группу, подходящую целевому фреймворку проекта.
  Поэтому в нашем графе может быть больше пакетов.
- **Диапазоны.** Исключающие границы трактуются как включающие.
- **SDK.** Зависимости SDK (метапакеты, подразумеваемые платформой), не
  описанные в `.nuspec`, не учитываются.
- **Циклы.** NuGet циклы не допускает; здесь они разрываются и показываются.
- **Глубина рекурсии.** Лимит рекурсии поднят до 5000; при его превышении
  выводится сообщение об ошибке.
- **Сервер PlantUML.** Для очень больших графов запрос не помещается в URL
  (предел 8000 символов); используйте `--plantuml-jar`.

## Сравнение со штатными инструментами

Для сравнения с реальным менеджером создайте проект и добавьте пакет:

```
dotnet new console -n cmp && cd cmp
dotnet add package Newtonsoft.Json --version 13.0.3
dotnet list package --include-transitive
dotnet nuget why cmp.csproj <пакет>   # в новых версиях SDK: цепочки зависимостей
```

Подробные данные — в `obj/project.assets.json`. Сравнивайте состав пакетов,
версии и пути зависимостей; расхождения объясняются пунктами из раздела
«Упрощения и ограничения». У `dotnet` нет понятия «порядок загрузки»: пакеты
скачиваются параллельно, а выводятся по алфавиту, поэтому сравнима только
корректность топологического порядка.

## Тесты

Запуск: `./run.sh test` или `python3 -m unittest discover -s tests -v`.
Сеть не используется: `http_get` и `urlopen` подменяются через
`unittest.mock`.

Что покрыто:

- проверка параметров: успешные и ошибочные случаи для каждой опции;
- тестовый репозиторий: цепочка, ромб, цикл, самоссылка, фильтр, ошибки
  формата файла с номером строки;
- порядок загрузки: зависимость стоит раньше зависимого, корень последний,
  цикл не приводит к зависанию;
- ASCII-дерево и текст PlantUML, включая кодировщик для сервера PlantUML
  (проверка «туда-обратно»);
- реальный режим на заглушках: service index (список/строка в `@type`, BOM,
  некорректный JSON), `.nuspec` (группы фреймворков, пространства имён,
  пакет без зависимостей), ошибки 404/500, таймаут;
- запуск `main` целиком: коды возврата 0/2/3/4, глубокая цепочка из 1500
  пакетов;
- ограничение цикломатической сложности функций (не больше 10).

Запуск на настоящем `api.nuget.org` и сравнение с `dotnet` нужно выполнить
отдельно на машине с доступом в интернет.

## Стиль кода

PEP8: имена в `snake_case`, строки не длиннее 80 символов, функции не длиннее
40 строк, без «магических» чисел в сравнениях (значения вынесены в именованные
константы). Сообщения коммитов — по спецификации Conventional Commits.
